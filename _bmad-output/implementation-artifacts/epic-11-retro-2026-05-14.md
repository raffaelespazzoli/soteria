## Key Insights

1. **"Smaller stories produce cleaner code."** (Raffa) The 5–7 AC sweet spot combined with tight scoping eliminates implementation friction. Zero-debug stories become the norm. This should remain a core team principle.

2. **"Simplification epics are high-value work."** Removing complexity (implicit driver derivation) is as valuable as adding features. Engine coverage improved from 83.4% to 86.7% purely through dead code removal. Net deletion is a quality signal.

3. **"Build-up patterns create natural dependency chains that reduce ambiguity."** Type → consumption sites → UI is a repeatable pattern. Each story has a clear input contract from the previous one. This pattern should be the default decomposition strategy.

4. **"Test infrastructure must precede the features it validates."** Epic 12's noop VolumeReplication controller (new Story 12.0) enables on-cluster UAT for all subsequent stories. Building it first prevents a UAT gap.

5. **"Explicit beats implicit."** The design decision to replace implicit PVC→SC→provisioner→driver derivation with an explicit `volumeReplicationDriver` field eliminated an entire class of runtime fragility. The same principle drives the new `volumeReplicationClass` field for Epic 12.

## Epic 12 Preparation — Significant Discovery

### New Story 12.0: Noop VolumeReplication Controller + volumeReplicationClass Field

**Discovery:** Epic 12's CSI Extension driver creates `VolumeReplication` and `VolumeGroupReplication` CRs, expecting a CSI Addons sidecar controller to reconcile them. On the test environment (etl6/etl7), no real CSI Addons operator exists. Without a stub controller, CRs will have empty status and Soteria's `GetReplicationStatus` will never see health signals.

**Decision (Raffa):** Add Story 12.0 as the first story of Epic 12 with the following scope:

1. **`volumeReplicationClass` field on DRPlanSpec** — free-form string (not enum), required, immutable. Same pattern as `volumeReplicationDriver` from Story 11.1. The CSI Extension driver stamps this class when creating VolumeReplication/VolumeGroupReplication CRs.

2. **Noop VolumeReplication controller** — lives in `pkg/controller/volumereplication/`, watches `VolumeReplication` and `VolumeGroupReplication` CRs filtered by `spec.volumeReplicationClass == soteria-noop`. Reconciles status to simulate successful CSI Addons operations (state transitions, health reporting).

3. **Class filtering** — controller only manages CRs with class `soteria-noop`. CRs with other classes are ignored, allowing real CSI Addons sidecars to manage their own classes.

4. **Types imported from upstream** — VolumeReplication/VolumeGroupReplication types imported from `github.com/csi-addons/kubernetes-csi-addons` module, not redefined.

**Impact on existing stories:** Stories 12.1–12.6 remain as-is, but the CSI Extension driver reads `plan.Spec.VolumeReplicationClass` when creating CRs.
